# Baseline

이 스킬은 두 작업에 사용합니다. 기존 프론트엔드 프로젝트를 지정된 Baseline에 따라 감사하거나, Baseline 기술 스택 기준으로 프론트엔드 프로젝트를 셋업합니다.

## 워크플로 하나를 선택해 읽기

- **프로젝트 감사 모드:** 사용자가 프로젝트 Context, Baseline 준수 여부 또는 구현 근거를 조사·감사·검토·평가해 달라고 할 때 사용합니다. [references/frontend-project-audit.md](references/frontend-project-audit.md)를 완전히 읽고 따릅니다. 이 모드는 기본적으로 읽기 전용입니다.
- **프로젝트 셋업 모드:** 사용자가 Baseline에 따라 아직 초기화되지 않은 대상에 프론트엔드 프로젝트를 생성·초기화·스캐폴딩·부트스트랩해 달라고 할 때 사용합니다. [references/frontend-project-setup.md](references/frontend-project-setup.md)를 완전히 읽고 따릅니다. 셋업 여부 gate를 항상 먼저 적용하며, 이미 프로젝트가 셋업된 대상에는 어떤 추가 셋업도 하지 않습니다. 이 모드에서 쓰기는 gate를 통과한 요청 대상 내부로만 제한됩니다.
- **결합 요청:** 두 워크플로 문서를 모두 읽습니다. 셋업 여부 gate를 통과하면 셋업을 먼저 완료하고 생성 결과를 확정된 FTS 선택과 대조해 검증합니다. 대상이 이미 셋업되어 있으면 셋업을 건너뛰고, 사용자가 프로젝트 감사도 요청한 경우에만 읽기 전용 감사를 실행합니다.

선택하지 않은 워크플로 문서는 읽지 않습니다. 일반적인 구현·디버깅·설명·코드 리뷰 요청은 사용자가 Baseline 감사나 Baseline 기반 셋업을 요청하지 않는 한 이 두 워크플로를 호출하지 않습니다.

## 공통 권한 모델

- 기본적으로 [references/BASELINE.md](references/BASELINE.md)와 여기에 열거된 모든 구성 파일을 지정된 조직 Baseline으로 사용합니다. 사용자가 다른 Baseline을 명시적으로 지정하면 그 단일 소스만 사용하고 어떤 소스가 결과를 규율했는지 밝힙니다. 여러 Baseline을 암묵적으로 병합하지 않습니다.
- 프로젝트를 감사하거나 셋업하기 전에 지정된 Baseline을 완전히 읽습니다. 인덱스 또는 구성 문서라면 선언된 모든 필수 구성 요소를 따라가 각각 완전히 읽습니다. 인덱스만으로는 그 인덱스가 참조하는 기준의 충분한 근거가 되지 않습니다.
- 지정된 Baseline을 이 스킬의 유일한 평가·셋업 프레임워크로 취급합니다. 프레임워크 관례, 일반적인 아키텍처 선호 또는 외부 문서 표준을 추가로 강제하지 않습니다.
- 지정된 Baseline의 모든 `FTS-*` 행을 조직 기술 스택 기준으로 취급합니다. 감사 모드에서는 프로젝트가 선언한 스택 및 관찰된 스택과 대조합니다. 셋업 모드에서는 관련 파일을 생성하기 전에 각 행을 프로젝트의 단일 선택으로 확정합니다.
- 프로젝트별 주장의 소유자는 프로젝트 Context입니다. Context가 여러 문서에 분산될 수 있지만, 중요한 각 사실에는 발견 가능한 소유자가 있어야 합니다.
- 코드, CI, 구성 및 런타임 결과를 이용할 수 있으면 현재 상태 주장의 근거로 취급합니다. 이 근거가 Context와 모순되면 `문서-코드 불일치`로 보고하고 어느 한쪽도 조용히 다시 쓰지 않습니다.
- Baseline 문구를 복사한 뒤 프로젝트 근거라고 부르지 않습니다. 프로젝트별 주장, 소유자, 범위 및 검증 경로가 필요합니다.
- 어느 모드도 관련 없는 인프라, 배포, 외부 계정, 자격 증명, 운영 데이터 또는 원격 저장소 변경을 허가하지 않습니다.

번들 참조와 명시적으로 지정된 Baseline을 모두 읽을 수 없다면 기준을 만들어내지 않습니다. 작업이 차단되었다고 보고하거나, 안전하게 진행할 수 없을 때 Baseline 위치를 요청합니다.

## 공통 Context 모델

Context를 읽거나 쓸 때 다음 주장 유형을 구분합니다.

- **현재 상태:** 지금 구현되어 있거나 사실인 내용
- **규칙:** 앞으로의 프로젝트 작업이 따라야 할 내용
- **결정:** 무엇을 선택했고 왜 선택했는지, 어떤 대안을 거부했으며 무엇을 대체했는지
- **계획:** 현재 상태가 아닌 향후 의도

계획을 구현 사실로 취급하지 않습니다. 코드가 아직 준수하지 않더라도 규칙은 규범적일 수 있으므로 구현 대조는 별도로 유지합니다.
