# 4. 대조 상태 용어

## 문서 상태

`답변`, `부분 답변`, `미답`, `라우팅 결함`, `미조사`

## 현재 상태

`구현됨`, `부분 구현`, `미구현`, `계획`, `범위 밖`, `폐기·대체됨`, `미확인`, `해당 없음`

## 대조 상태

`일치`, `문서-코드 불일치`, `대조 불가`, `미대조`, `계획이라 대조하지 않음`

## 검증 상태

`통과 증거`, `실패 증거`, `부분 증거`, `미실행`, `실행 차단`, `해당 없음`

## Agent 상태

`완료`, `부분`, `실패`, `차단`, `timeout`

이 용어들은 점수가 아닙니다. unknown, not compared, uncheckable, blocked, not investigated 상태는 그대로 드러나야 합니다.

## 쉬운 보고 라벨

최종 보고서에서는 위의 세부 상태를 근거로 유지하되, 사용자가 결과를 바로 이해할 수 있도록 각 발견 사항에 다음 쉬운 라벨을 붙입니다.

| 쉬운 결과 | 언제 사용하는가 | 쉬운 설명 |
| --- | --- | --- |
| `문제 없음` | 필요한 Context가 있고 구현과 일치하며 필요한 검증 근거가 있음 | 문서와 실제 동작이 맞습니다. |
| `Context 부족` | 필요한 답, 규칙, 결정, 소유자 또는 라우팅 선언이 없거나 불완전해 기대 상태를 확정할 수 없음 | 프로젝트 설명이 부족해 무엇이 맞는지 판단하기 어렵습니다. |
| `Context 부패` | 존재하는 Context가 서로 모순되거나, 없는·잘못된 대상을 가리키거나, 현재 상태라고 쓴 내용이 실제 코드·구성과 충돌함 | 문서가 낡았거나 깨져 실제 프로젝트를 잘못 설명합니다. |
| `미구현` | 적용되는 요구·규칙·결정은 명확하지만 대응하는 코드 또는 필수 구성 자체가 없음 | 해야 한다고 정해졌지만 아직 만들어지지 않았습니다. |
| `부분 구현` | 요구 일부만 구현됐거나 필수 경로·상태·검증 중 일부만 있음 | 일부는 있으나 완료되지 않았습니다. |
| `기준 불일치` | Context와 구현은 서로 맞더라도 선택이 Baseline의 기본·허용 범위를 벗어남 | 프로젝트 선택이 조직 기준에 맞지 않습니다. |
| `검증 실패` | build, type check, lint, test 또는 runtime 검증에서 실제 실패를 관찰함 | 실행해 본 검사에서 문제가 확인됐습니다. |
| `확인 불가` | 필요한 코드, 실행 환경 또는 검증 근거에 접근할 수 없어 판단할 수 없음 | 자료나 실행 환경이 없어 확인하지 못했습니다. |
| `계획` | Context가 미래 의도로 명시했고 현재 구현을 약속하지 않음 | 앞으로 할 일이지만 현재 완료 항목은 아닙니다. |
| `범위 밖` | 사용자가 정한 감사 경계에 포함되지 않음 | 이번 조사 대상이 아닙니다. |
| `해당 없음` | 범위 안을 조사했으며 프로젝트에 적용될 surface가 없음 | 이 프로젝트에는 적용되지 않습니다. |

라벨은 세부 상태를 대체하지 않습니다. 다음 구분을 지킵니다.

- Context가 없거나 답이 부족하면 구현 여부부터 단정하지 않고 `Context 부족`을 사용합니다.
- Context가 현재 구현됐다고 주장하지만 코드가 없으면 쉬운 결과는 `Context 부패`로 보고하고, 세부 현재 상태에는 `미구현`을 남깁니다.
- Context가 요구·규칙·결정을 명확히 선언했지만 완료됐다고 주장하지 않았고 코드가 없으면 `미구현`을 사용합니다.
- Context와 코드가 다르면 어느 쪽이 Baseline에 맞더라도 `Context 부패`를 사용하고 세부 대조 상태에는 `문서-코드 불일치`를 유지합니다.
- Context와 코드가 서로 일치하지만 선택 자체가 Baseline을 벗어나면 `Context 부패`가 아니라 `기준 불일치`를 사용합니다.
- 검사를 실제로 실행해 실패를 관찰하면 `검증 실패`를 사용합니다. 실패 하나만으로 구현 전체가 없다고 단정하지 않습니다.
- 단지 실행하지 못했거나 근거에 접근할 수 없다는 이유로 `미구현` 또는 `Context 부패`라고 하지 않고 `확인 불가`를 사용합니다.

각 발견 사항은 다음 순서의 한두 문장으로 씁니다.

```text
[쉬운 결과] 무엇이 문제인지 — 확인한 문서·코드 근거. 사용자 또는 개발 작업에 미치는 영향. 가장 작은 다음 행동.
```

내부 상태 이름만 나열하거나 `Context 부족` 같은 라벨만 단독으로 쓰지 않습니다. 무엇이 부족하거나 깨졌는지, 어떤 실제 근거와 비교했는지를 평이한 말로 설명합니다.
