# 5. 경계가 Context를 제한하는 방식

경계는 Context 답변이 무엇을 확인 가능하게 만들어야 하는지 설명하며, 프로젝트 구현 방식을 지정하지 않습니다. Context claim은 프로젝트가 해당 사실을 소유하는 위치를 가리키고, 관련이 있으면 적용되는 경계 ID를 밝혀야 합니다. 경계 문장을 그대로 복사해 근거라고 부르면 안 됩니다.

사람이 읽기 쉽게 21개 경계를 11개의 알기 쉬운 주의사항으로 요약하면 다음과 같습니다.

1. 비밀값과 최종 권한 판정을 브라우저 밖에 두고, 외부 값은 들어오는 순간 확인합니다.
2. 생성 산출물은 원본에서 바꾸고, 의존성 방향에 순환이 생기지 않게 합니다.
3. 각 사실의 최종 소유자를 하나로 정하고, 상태 변경 실패나 순서가 뒤바뀐 결과의 처리 방식을 정의합니다.
4. 실패를 숨기지 말고 요청, listener, timer, subscription을 남겨 두지 않습니다.
5. 공개 route, props, API, event, storage 계약을 호환되게 유지하거나 전환 방법을 기록합니다.
6. 의미 있는 컨트롤을 통해 실제 loading, empty, error, success, stale, recovery 상태를 보여줍니다.
7. 검증과 범위를 보존하고, 재현 가능한 실행 근거와 함께 완료를 보고합니다.
8. 코드 품질 gate의 범위와 통과 조건을 명시하고, 제외·우회에는 소유자와 만료 조건을 둡니다.
9. 비즈니스 규칙의 최종 구현 소유자를 하나로 두고 UI와 모듈이 공개 계약을 통해 소비하게 합니다.
10. 주요 route와 흐름의 성능 목표, lab·field 측정 조건, gate·모니터링과 초과 예외를 정의합니다.
11. 보안 통제와 취약점의 처리 책임을 정하고, 신뢰하지 않는 값을 화면에 출력할 때는 출력 위치에 맞게 안전하게 처리합니다.

이 주의사항은 읽기 위한 요약입니다. 검토 의견에서는 `ST-3`, `UX-1`과 같은 원자 ID를 사용해 발견 사항의 의미를 하나로 고정합니다. `해당 없음`에는 이유가 필요하며, 경계를 약화해도 된다는 뜻이 아닙니다.
