# 1. 주제 (고정 분모: 8)

| 주제 | Context가 답해야 하는 질문 |
| --- | --- |
| **Product & Domain (제품·도메인)** | 제품은 누구를 위한 것이며 무엇을 하는가? 핵심 흐름, 도메인 용어, 비즈니스 규칙, 현재 제한 사항, 요구사항·백로그의 정본은 무엇인가? |
| **Stack & Commands (기술 스택·명령어)** | 어떤 조직 기본값·허용 대안·금지·지원 종료 정책이 적용되는가? 프로젝트가 실제 선택한 언어, runtime, framework, rendering 방식, build tool, package manager, lockfile, test tool, 배포 대상은 무엇인가? 설치·실행·빌드·검증 명령과 dev server 주소는 어디인가? |
| **Structure & Routing (구조·라우팅)** | 각 디렉터리의 소유 범위는 무엇인가? 허용된 의존성 방향은 무엇인가? 라우팅은 누가 소유하며 route parameter는 어떻게 표현하고 컴포넌트 파일은 어떻게 나누고 이름 짓는가? |
| **State Ownership (상태 소유권)** | 서버, 전역 클라이언트, URL, 폼 상태는 누가 소유하는가? 서로 경쟁하는 비동기 응답을 해결하는 규칙은 무엇인가? |
| **UI & Styling (UI·스타일링)** | 스타일은 어떻게 작성하며 token과 공용 컴포넌트는 누가 소유하는가? 프로젝트에 맞는 상호작용·접근성 동작은 무엇인가? |
| **Data Access (데이터 접근)** | 외부 데이터의 흐름은 무엇인가? base URL, timeout, retry, 오류, 인증, 권한, 환경 변수, runtime 배포 문제는 어디에 정의되어 있는가? |
| **Verification (검증)** | 각 단계에서 무엇을 검증하는가? 기대값은 어디서 오며 테스트는 어디서 어떤 방식으로 실행하는가? 코드 품질·성능·보안 gate의 통과 조건과 적용 범위는 무엇인가? 주요 route·흐름의 성능 budget은 어떤 lab·field 환경에서 측정하며 CI·hook·운영 모니터링을 막거나 경고하는 조건과 시각적 동작 검증 방법은 무엇인가? |
| **Decisions (의사결정)** | 되돌리기 어려운 선택은 무엇이며 왜 결정했는가? 어떤 결정이 다른 결정으로 대체되었는가? |

Runtime & Delivery는 의도적으로 9번째 주제가 아닌 여러 주제에 걸친 질문으로 둡니다. Stack & Commands, Data Access, Verification을 통해 답합니다.

코드 품질, runtime·UX 성능 품질과 보안도 별도 주제가 아니라 모든 주제에 적용되는 횡단 기준으로 둡니다. 적용되는 품질·보안 주장에는 기준, 범위, 소유자, 강제 또는 검증 방법, 근거, 예외 소유자와 만료 조건이 있어야 합니다.

- **코드 품질과 설계:** type safety, lint·format·static analysis, 테스트와 build gate, 컴포넌트·모듈 책임, 비즈니스 규칙의 최종 구현 소유자, 의존성 방향, 좁고 안정적인 공개 surface와 변경 파급 범위를 드러냅니다. SOLID와 deep module은 이름 자체를 준수시키는 체크리스트가 아니라 응집도·결합도·캡슐화 결함을 설명하는 검토 관점으로 사용합니다. 도구와 정량 임계값은 Baseline이 명시하지 않은 한 프로젝트 Context가 근거와 함께 소유합니다.
- **Runtime·UX 성능 품질:** 주요 route와 사용자 흐름에 적용되는 성능 지표, 기대값 출처, lab·field 구분, device·network·표본·percentile 등 측정 조건, budget, gate·운영 모니터링, 회귀와 예외의 소유자를 드러냅니다. 개별 지표 이름을 영구 규칙으로 고정하지 않고 프로젝트가 적용하는 현재 지표와 기준 출처를 기록합니다.
- **보안:** 보호 자산과 위협, 신뢰 경계, 외부 입력과 출력, 인증·권한, 비밀값·개인정보, 의존성 공급망, 보안 통제·취약점·예외의 처리 기준과 대응 소유자를 드러냅니다. 신뢰하지 않는 콘텐츠를 화면에 출력하는 경로는 출력 컨텍스트별 encoding 또는 승인된 sanitization 경계와 검증 근거를 밝혀야 합니다.

## 완전한 Context 답변이 드러내야 하는 것

모든 주제는 다음 세 종류의 사실을 드러내야 합니다.

- **아키텍처:** 경계, 소유권, 의존성 방향, runtime 흐름, 앱 또는 workspace의 범위
- **디자인:** 사용자 의도, 화면·상호작용 상태, 계약, UI 결정, 프로젝트에 맞는 반응형·접근성 동작
- **엔지니어링:** 실행 가능한 명령어, 실패·정리 동작, 테스트와 기대값, 배포 가정, 주장을 뒷받침하는 근거

8개 주제는 근거 없이 특정 라이브러리나 폴더 배치를 요구하는 것이 아닙니다. 조직이 정한 기술 스택 기준과 프로젝트가 실제 선택한 아키텍처, 소프트웨어 디자인, 엔지니어링 방식을 함께 찾아낼 수 있도록 하는 질문입니다.

- Product & Domain은 사용자, 핵심 화면, 정상·오류·빈 상태·권한 흐름, 도메인 규칙, 현재 공백, 요구사항 정본을 드러냅니다.
- Stack & Commands는 조직 기본값과 허용 범위, 프로젝트가 선택한 언어·runtime·framework·rendering·build·test 기술, 정본 패키지 관리자와 lockfile, workspace 경계, 지원 브라우저, 배포 환경, 명령어, dev server 주소를 드러냅니다.
- Structure & Routing은 모듈 소유권, 허용된 의존성 방향, route·parameter 정본, 생성 산출물, 파일 이름 규칙의 경계를 드러냅니다.
- State Ownership은 동기화·경쟁 조건을 포함해 서버·클라이언트·URL·폼·파생·영속 상태의 소유자와 수명을 드러냅니다.
- UI & Styling은 token·컴포넌트 소유권, 반응형 결정, 상호작용 의미, 화면에 보이는 UI 상태와 실제 상태의 일치 방식을 드러냅니다.
- Data Access는 외부 경계, 검증·매핑, 오류, 인증·권한, 환경 주입, 취소, 배포 연계를 드러냅니다.
- Verification은 기대값의 출처, 테스트 계층, 단일·전체 테스트 명령어, 코드 품질·성능·보안 gate의 범위와 통과 조건, lab·field 성능 근거, 예외, CI gate와 운영 모니터링, 시각 검증, 재현 가능한 실행 근거를 드러냅니다.
- Decisions는 이후 변경이 이력을 조용히 덮어쓰지 않도록 되돌리기 어려운 선택, 대안, 소유자, 범위, 대체된 결정을 드러냅니다.
