# 프론트엔드 프로젝트 감사

사용자가 프론트엔드 프로젝트의 Context, Baseline 준수 여부 또는 구현 근거를 조사·감사·검토·평가해 달라고 할 때만 이 워크플로를 사용합니다.

## 결과물

프로젝트의 유효한 Context 경로, 답변 범위, FTS 기술 스택 준수 여부, 최소 규칙 및 Context와 구현의 일관성을 근거에 따라 읽기 전용으로 평가합니다. 최종 결과는 `Context 부족`, `Context 부패`, `미구현` 같은 쉬운 라벨과 평이한 설명으로 먼저 요약하고, 정확한 세부 상태와 근거를 뒤에 둡니다. 사용자가 별도로 변경을 요청하지 않는 한 Context, 코드, 구성 또는 Baseline 파일을 편집하지 않습니다.


## 1. 깊이 읽기 전에 목록 만들기

문서를 순서대로 읽기 전에 저장소와 작업 트리의 목록을 만듭니다. 완전한 목록은 “모든 파일 읽기”가 아니라 후보 파일과 제외 항목을 재현 가능하게 기록한 것입니다.

다음과 같은 읽기 전용 탐색을 사용합니다.

```bash
git ls-files
rg --files -uu -g '!.git/**'
rg --files -uu -g '!.git/**' | rg '\.(md|mdx|txt|adoc|rst)$'
```

`README`, `AGENTS`, `CLAUDE`, `CONTEXT`, `CONTRIBUTING`, ADR·결정 문서, 패키지·workspace manifest, CI 정의, 환경 예시 및 테스트 구성을 포함해 관례상 소스와 프로젝트가 선언한 소스도 조사합니다. 이름이 `context`가 아니어도 Context 문서 또는 보조 근거일 수 있습니다.

모든 후보를 다음 중 하나로 분류합니다.

- Context 후보
- 보조 근거
- 생성 산출물
- 외부·vendor 문서
- 임시 또는 보관 문서
- 범위 밖

무시되거나 추적되지 않거나 생성됐거나 참조된 파일을 조용히 생략하지 않습니다. 탐색 범위와 제외 이유를 기록합니다. Context 후보 문서의 링크와 텍스트 참조를 따라가며, 참조된 소유자와 근거 소스를 후보 집합에 포함합니다.

## 1a. 유효한 Context 라우팅 지도 만들기

문서 링크와 유효한 Context 경로를 혼동하지 않습니다. 링크는 문서를 발견 가능하게 만들 뿐이며, 문서가 작업 또는 Baseline 항목에 적용되고 에이전트 지침 체인에서 도달 가능할 때만 경로가 유효합니다. 실제 답변 또는 규칙 근거가 되려면 대상을 읽어야 하며, 읽기로 명시적으로 예정된 것은 계획된 소비일 뿐 근거가 아닙니다.

경로를 확정하기 전에 감사 모드를 결정합니다.

- **Context 감사:** 8개 주제와 공통 코드 설계·성능·보안 기준에 필요한 모든 경로, 지정된 Baseline에 있는 모든 `FTS-*` 기술 스택 항목 및 21개 최소 규칙·거버넌스 ID를 열거합니다.
- **작업 범위 감사:** 사용자가 Context 감사를 요청하면서 특정 작업 또는 영역으로 제한할 때만 사용합니다. 일반 구현·디버깅·설명 요청은 이 감사 모드를 호출하지 않습니다.

작업 범위 감사에서는 다음을 수행합니다.

1. 사용자가 요청한 작업 또는 영역을 감사 경계로 사용합니다.
2. 직접 관련된 영역과 이 작업으로 영향을 받는 실제 consumer 또는 의존성의 Context 경로를 포함합니다.
3. 해당 경계와 연결된 Baseline 질문, `FTS-*` 항목 및 최소 규칙·거버넌스 ID만 적용합니다.
4. 관련 없는 주제, FTS 항목, 경로 및 규칙 ID는 `범위 밖`으로 기록합니다. 결함이나 `해당 없음`으로 보고하지 않습니다.
5. 경계 안에서 적용 상태, 경로 무결성 및 답변 범위를 별도로 평가합니다. 필수 경로가 누락됐거나 도달할 수 없으면 라우팅 결함이고, 불완전한 답변은 답변 범위 결과입니다.

`범위 밖`은 사용자가 감사를 제한해 해당 영역을 조사하지 않았다는 뜻입니다. `해당 없음`은 범위 안에서 영역을 조사했지만 관찰된 프로젝트 surface에 규칙이 적용되지 않는다는 뜻입니다. 이용 가능한 Context와 근거가 불충분할 때 두 상태 중 어느 것도 `미확인` 대신 사용하지 않습니다.

다음 상태 차원을 독립적으로 유지합니다.

- **적용 상태:** `적용`, `해당 없음`, `미확인`, `범위 밖`
- **경로 상태:** `정상`, `라우팅 결함`, `미조사`, `범위 밖`
- **답변 상태:** `답변`, `부분 답변`, `미답`, `미조사`, `범위 밖`

경로 상태가 `라우팅 결함`이면 경로 선언 없음, 대상 누락, 대상 도달 불가, 범위 불일치 또는 잘못된 대상 중 구체적 이유를 하나 이상 기록합니다. `라우팅 결함`은 답변 상태가 아닙니다.

대상 에이전트 또는 작업 디렉터리를 안다면 활성 구성과 문서화된 동작에서 에이전트의 지침 로딩 범위 및 우선순위를 파악합니다. 최소한 다음을 구분합니다.

- 시작 시 자동 로드
- import 또는 명시적으로 포함
- 경로 범위 또는 요청 시 로드
- 일반 링크 또는 텍스트 참조로만 도달 가능
- 도달 불가, 제외 또는 로드 가능 여부 미확인

일반 Markdown 링크가 import라고 가정하지 않습니다. 모든 `AGENTS.md`, `CLAUDE.md` 또는 중첩 규칙 파일이 모든 작업에 로드된다고 가정하지 않습니다. 여러 에이전트가 범위에 포함되면 로드 동작을 합치지 말고 에이전트마다 별도의 유효 경로를 만듭니다.

모든 경로 선언에서 링크를 선언 문서 기준으로 해석하고 다음을 기록합니다.

```text
작업 조건 또는 Baseline 질문/FTS/ID
→ 경로 선언 위치
→ 경로 조건
→ 대상 문서
→ 에이전트와 범위
→ 로드 방식
→ 실제 읽음 여부
→ 소유자와 근거
→ 적용 상태
→ 경로 상태 및 결함 원인
→ 답변 상태
```

대상이 존재한다는 이유만으로 경로가 완전한 것은 아닙니다. 적용되는 모든 대상을 따라가고 그 내용에서 관련 질문 또는 규칙에 답합니다. 열거됐지만 읽지 않은 대상은 `실제 읽음 여부: 아니오`로 기록해야 하며 근거가 아닙니다. 필수 대상이 누락됐거나 도달할 수 없거나 선언된 범위 밖 문서를 가리키거나 관련 질문·ID에 연결되지 않으면 `라우팅 결함`입니다.

## 2. 목록을 Baseline 8개 주제로 연결하기

전체 Context 감사에서는 고정 분모인 다음 8개 주제를 사용합니다.

1. Product & Domain
2. Stack & Commands
3. Structure & Routing
4. State Ownership
5. UI & Styling
6. Data Access
7. Verification
8. Decisions

코드 설계·성능·보안은 주제 분모를 늘리지 않는 공통 기준으로 평가합니다. 각 주제에서 적용되는 품질·보안 주장에 기준, 범위, 소유자, 강제·검증 방법, 근거, 예외 소유자와 만료가 있는지 질문-경로 지도에 함께 연결합니다. 코드 품질·설계와 lab 성능 gate는 기본적으로 프로젝트의 `software.md` 또는 동등한 소유자에서, 사용자 체감 성능 목표는 `ui-ux.md`, field 수집·운영 경보는 `system.md`, 보안 정책은 `security.md` 또는 각각의 동등한 소유자에서 찾되 파일 이름만으로 소유권을 추론하지 않습니다.

작업 범위 감사에서는 정의된 경계와 연결된 주제 및 하위 질문만 평가합니다. 제외된 주제는 보고서에 `범위 밖`으로 명확히 남기되, 8개 주제 분모를 채우기 위해 조사하지 않습니다.

문서를 선택하기 전에 각 주제의 Baseline 질문을 명시된 하위 질문으로 분해합니다. 질문-경로 지도를 만든 다음 각 하위 질문의 대표 소스를 식별합니다. 관련 없는 문서를 깊이 읽지 않되, 하위 질문에 답하는 데 필요한 적용 가능한 경로 대상은 모두 읽습니다. 주제가 다음 세 종류의 사실을 모두 드러내는지 기록합니다.

- 아키텍처: 경계, 소유권, 의존성 방향, runtime 흐름 및 범위
- 디자인: 사용자 의도, 화면과 상호작용 상태, 계약, 반응형 동작 및 접근성 동작
- 엔지니어링: 실행 가능한 명령어, 실패와 정리 동작, 테스트와 기대값, 배포 가정 및 근거

전체 Context 감사에서는 대표 문서 하나를 찾았다고 멈추지 않습니다. 한 경로가 신규 기능 워크플로는 다루면서 도메인 규칙, 현재 제한 또는 요구사항·backlog 소유권에는 답하지 않을 수 있으므로, 해당 주제로 이어지는 선언된 모든 조건을 확인합니다.

## 2a. 모든 Baseline 기술 스택 항목 대조하기

개수를 하드코딩하지 말고 지정된 Baseline에서 기술 스택 분모를 발견합니다. ID가 `FTS-*`인 모든 표 행은 독립적인 대조 항목입니다. ID, 범주, 결정 항목, 조직 기본값 및 Baseline 상태를 작성된 그대로 보존합니다. 중복 ID, 잘못된 행 또는 미확정 Baseline 값은 Baseline 결함이며 감사 중 조용히 고치거나 추론하지 않습니다.

전체 Context 감사에서는 발견된 모든 FTS 항목을 대조합니다. 작업 범위 감사에서는 요청된 경계 또는 영향을 받는 consumer와 의존성에 연결된 각 FTS 항목을 대조하고, 나머지는 모두 `범위 밖`으로 기록합니다.

범위 안의 각 FTS 항목에 대해 다음을 수행합니다.

1. 프로젝트의 실제 선택을 소유해야 하는 Context 경로를 확정합니다. 코드 또는 구성 근거가 누락된 Context 소유자나 깨진 경로를 고쳐주지는 않습니다.
2. Context가 선언한 프로젝트 선택을 기록합니다. 신뢰할 수 있는 선언이 없으면 `미답` 또는 `미확인`을 유지합니다.
3. 관찰된 선택에 이용 가능한 근거를 조사합니다. 일반적인 근거에는 패키지·workspace manifest, 정본 lockfile, compiler·build·test·lint 구성, 소스 import, CI workflow, 배포 구성 및 초기화된 runtime SDK가 있습니다.
4. 선언된 선택을 Baseline 기준과 대조한 다음, 관찰된 선택을 양쪽과 대조합니다. Context와 구현이 다르면 어느 한쪽이 Baseline을 준수하더라도 `문서-코드 불일치`로 보고합니다.
5. lockfile에 나타난다는 이유만으로 설치된 의존성이 활성 선택이라고 추론하지 않습니다. FTS 역할에 맞는 직접 의존성, 구성, 스크립트, import, 생성 산출물 소유자, CI 사용 또는 실행 근거를 우선합니다.

Baseline 상태와 행 문구를 확장하지 않고 해석합니다.

- `기본`: 명시된 기본값과 일치하면 `기본 일치`입니다. 다른 선택은 조직이 승인한 결정에서 명시적으로 허용하지 않는 한 `불일치`입니다.
- `허용`: 행에 명시적으로 열거된 선택은 `허용된 선택`입니다. 프로젝트 단위 자유 선택 또는 선택적 미사용 같은 문구는 해당 행에만 효력이 있습니다.
- `기본·허용`: 명시된 기본값은 `기본 일치`이고, 명시적으로 허용된 대안은 `허용된 선택`입니다.
- `미결정`: `기준 미결정`을 사용하며 기존 프로젝트 코드를 조직 기본값으로 만들지 않습니다.
- `해당 없음`: Baseline 행과 조사한 프로젝트 surface가 뒷받침할 때만 `해당 없음`을 사용합니다.

**스택 준수 상태**를 경로, 답변, 현재 상태, Context-코드 대조 및 검증 상태와 분리합니다. 스택 준수에는 `기본 일치`, `허용된 선택`, `불일치`, `기준 미결정`, `미확인`, `해당 없음`, `범위 밖`만 사용합니다. Context 선택과 관찰된 구현의 준수 결과가 다르면 하나로 합치지 말고 둘 다 보고합니다.

## 3. 원자적 주장 추출하기

문서 전체를 똑같이 중요하게 취급하지 말고 주장을 검토합니다. 중요한 각 주장에 대해 다음을 기록합니다.

- 프로젝트별 언어로 작성한 주장 문구
- 주장 유형: 현재 상태, 규칙, 결정 또는 계획
- 정본 소유자와 범위
- 소스 문서와 섹션
- consumer, 참조 또는 영향을 받는 모듈
- 적용되는 Baseline FTS 항목과 규칙 ID
- 근거 또는 검증 경로
- 모순, 예외 및 migration 동작

Context는 프로젝트의 운영 지식과 규칙으로 기능해야 합니다. 프로젝트가 소유자, 순서 규칙, 실패 동작 및 검증 방법을 명시할 수 있는데도 “비동기 상태를 적절히 관리한다”처럼 모호하게 작성하면 불충분합니다.

## 3a. 확정된 경로를 통해 답하기

모든 Baseline 하위 질문과 범위 안의 FTS 항목은 유효한 경로의 Context를 읽은 뒤에만 답합니다. 다음 기록을 분리합니다.

- **경로 범위:** 질문 또는 규칙에 적용되는 경로가 있는지
- **경로 도달 가능성:** 대상 에이전트와 범위에서 target을 로드할 수 있는지
- **소비:** 이번 감사 중 target을 실제로 읽었는지
- **답변 범위:** target이 질문의 어느 부분을 뒷받침하는지
- **근거 범위:** 어떤 주장에 코드, 구성, 테스트 또는 실행 근거가 있는지

다음과 같은 경로에서도 이 구분을 사용합니다.

```text
신규 기능/흐름 변경 → PRD.md, ARCHITECTURE.md
도메인 규칙 변경 → DATA_MODEL.md, ARCHITECTURE.md
```

신규 기능이면서 도메인 규칙도 바꾸는 작업의 유효 집합에는 세 문서가 모두 포함됩니다. 전체 감사에서는 두 조건부 경로를 모두 조사하고, Product & Domain의 사용자, 흐름, 용어, 규칙, 제한 및 요구사항·backlog 하위 질문이 각각 다뤄지는지 확인합니다. `README.md`는 Product & Domain 답변 소스가 아니면서 Stack & Commands 또는 Verification의 유효 근거일 수 있습니다.

경로 target이 존재하고 도달 가능하며 올바른 소유자이지만 내용이 불완전하면 경로 상태는 `정상`, 답변 상태는 `부분 답변` 또는 `미답`을 사용합니다. 경로가 잘못된 종류의 문서를 가리키거나 필수 질문·규칙의 소유자로 이어지지 않으면 경로 상태를 `라우팅 결함`으로 하고 `잘못된 target` 또는 적용되는 구체적 이유를 기록한 다음, 답변 상태는 별도로 기록합니다. 프로젝트별 소유자, 범위 및 근거 없이 Baseline 규칙을 일반적으로 복사한 것은 답변이 아닙니다.

## 4. 선택적 심층 검토 분류

임의의 파일이 아니라 주장을 우선합니다.

**P0 — 감사 범위에서 항상 심층 검토**

- 브라우저·server 권한, 비밀값 또는 최종 권한 판정과 관련된 주장 (`TB-1`)
- 문서화된 검증·변환 소유자 없이 시스템에 들어오는 외부 값 (`TB-2`)
- 중복되거나 경쟁하는 소유권 (`ST-1`)
- 실패 시 실제 결과와 맞추는 규칙이 없는 optimistic 변경 또는 여러 단계 변경 (`ST-2`): 작업 제목만 보지 말고 영향을 받는 consumer와 의존성을 포함한 범위 안의 실제 프로젝트 흐름에서 적용 여부를 판단합니다.
- 경쟁하는 비동기 결과 (`ST-3`)
- 숨겨진 실패 또는 누락된 정리 (`RT-1`, `RT-2`)
- 공개 route, props, API, event 또는 storage 계약 (`IC-1`)
- loading, empty, error, success, stale 또는 recovery 동작 (`UX-1`, `UX-2`)
- 범위·통과 조건이 없거나 제외·우회의 소유자와 만료가 없는 코드 품질 gate (`CQ-1`)
- UI 컴포넌트가 비즈니스 규칙의 경쟁 소유자이거나 공유·독립 검증 대상 규칙이 명시된 모듈 경계와 공개 계약 없이 소비되는 구조 (`CQ-2`)
- 주요 route·흐름의 성능 지표·기대값 출처·측정 환경·목표·소유자·gate 또는 모니터링과 초과 예외가 없는 경우 (`PQ-1`)
- 검증·처리 기준, 소유자 또는 예외 만료가 없는 보안 통제와 취약점 (`SQ-1`)
- 신뢰하지 않는 값이 보호되지 않은 raw HTML·DOM 또는 그 밖의 위험한 출력 위치에 도달하는 경로 (`SQ-2`)
- 약화된 테스트, 누락된 실행 근거 또는 범위 밖 변경 (`VP-1`, `VP-2`, `VP-3`, `RP-1`)
- 모순되는 문서, 누락된 소유자 또는 참조됐지만 없는 소스

**P1 — 열린 문제와 연결될 때 심층 검토**

- 여러 주제 또는 모듈에서 참조되는 문서
- 프로젝트 전체 명령어, 공용 client, 전역 상태, 라우팅 규칙, 공용 컴포넌트, CI gate 또는 배포 가정
- Context, manifest, 구성, import, CI, 배포 또는 runtime 근거 사이에서 일치하지 않는 FTS 선택
- 불완전한 답변, 모호한 문구, 범위 없는 규칙 또는 대안과 대체 이력이 없는 결정
- 원본 또는 생성기가 불분명한 생성 산출물 (`SD-1`) 또는 순환 가능성이 있는 의존성 구조 (`SD-2`)

**P2 — 표본 검토 또는 연기**

- 명확한 소유자 하나가 있는 완전하고 구체적인 주장
- 모순 또는 고위험 규칙 연결이 없는 항목
- 제외 이유가 기록된 중복·생성·외부·보관 또는 영향이 낮은 자료

P0 또는 P1 주장이 다른 문서를 참조하면 소유자, 범위, consumer 영향 및 검증 경로가 확립되거나 참조가 명백히 끊겼음이 확인될 때까지 따라갑니다.

## 5. 21개 최소 규칙 및 거버넌스 항목 검사하기

Baseline에서는 이를 원자적 경계라고 부르지만, 운영상 **최소 규칙·거버넌스**로 보고합니다. ID와 21개 단일 분모를 유지하면서 다음 그룹을 분리합니다.

- **Context/runtime 최소 규칙(12개):** `TB`, `SD`, `ST`, `RT`, `IC`, `UX`
- **코드 설계·성능·보안 최소 규칙(5개):** `CQ-1`, `CQ-2`, `PQ-1`, `SQ-1`, `SQ-2`
- **검토·근거 거버넌스(4개):** `VP-1`, `VP-2`, `VP-3`, `RP-1`

적용되는 각 ID에서 Context가 일반 규칙을 프로젝트별로 소유되고 범위가 있으며 검증 가능한 규칙으로 만드는지 확인합니다. `해당 없음`은 이유가 있을 때만 허용합니다. 복사한 Baseline 문장을 근거로 인정하지 않습니다.

전체 Context 감사에서는 다음 21개 ID 각각의 유효 경로를 독립적으로 확정합니다. 작업 범위 감사에서는 정의된 경계와 연결된 ID를 판단하고 그 경로를 독립적으로 확정한 뒤, 나머지 ID는 `범위 밖`으로 기록합니다. 규칙 소유자와 근거로 이어지지 않는다면 주제 수준 경로만으로는 충분하지 않습니다.

`TB-1`, `TB-2`, `SD-1`, `SD-2`, `ST-1`, `ST-2`, `ST-3`, `RT-1`, `RT-2`, `IC-1`, `UX-1`, `UX-2`, `CQ-1`, `CQ-2`, `PQ-1`, `SQ-1`, `SQ-2`, `VP-1`, `VP-2`, `VP-3`, `RP-1`.

모든 ID에 대해 다음을 기록합니다.

- 규칙이 적용되게 하는 작업 조건
- 적용 상태
- 프로젝트별 규칙을 소유하는 Context 문서
- 경로가 이어지는 consumer, 코드·구성 또는 검증 소스
- 경로가 시작 시 로드, import, 경로 범위, 요청 시 로드, 링크 전용 또는 도달 불가 중 무엇인지
- 경로의 규칙과 근거를 실제로 읽었는지
- 경로 상태와 구체적인 라우팅 결함 이유
- 답변 상태와 누락된 소유자, 범위, 예외, 복구 또는 강제 방식

현재 작업 제목만이 아니라 감사 경계 안에서 문서화되고 관찰 가능한 프로젝트 surface를 통해 적용 여부를 판단합니다. 작업으로 영향을 받는 실제 consumer와 의존성을 포함합니다. 예를 들어 감사 요청에 “optimistic UI”라는 말이 없어도 범위 안의 흐름에 optimistic 상태 변경이나 여러 단계 상태 변경이 있으면 `ST-2`가 적용됩니다. 이용 가능한 Context와 근거에서 적용 여부를 판단할 수 없다면 `해당 없음`이 아니라 `미확인`을 사용합니다. 관련 surface를 범위 안에서 조사했고 어떤 작업 조건도 ID를 적용되게 하지 않을 때만 `해당 없음`을 사용합니다. 사용자가 요청한 경계에서 surface가 제외됐으면 `범위 밖`을 사용합니다.

`CQ-2`에서는 컴포넌트와 모듈의 책임을 rendering, interaction, orchestration, business rule로 구분하고 비즈니스 규칙의 구현 소유자, 중복 구현, 공개 surface, 의존성 방향, consumer와 독립 테스트 경로를 조사합니다. SOLID 또는 deep module이라는 용어가 문서에 있는지를 채점하지 않고, 책임 응집도, 결합도, 캡슐화, 내부 복잡성 누출과 변경 파급 근거로 구체적인 결함을 보고합니다. 무조건 hook·service를 추출하거나 계층 수를 늘리는 것을 준수로 간주하지 않습니다.

`PQ-1`에서는 주요 route·사용자 흐름별 적용 지표와 기대값 출처, lab·field 구분, device·network·traffic segment·표본·percentile·기간 같은 측정 조건, 목표·회귀 budget, gate·운영 모니터링, 소유자와 초과 예외 만료를 독립적으로 확인합니다. Lab 결과를 field 통과로, 단일 lab 점수를 실제 사용자 분포로 간주하지 않습니다. Field 자료가 없는 초기 프로젝트는 lab 결과와 field 수집 계획의 소유자·다음 행동을 분리하고 운영 성능을 `미확인` 또는 `미실행`으로 유지합니다. 외부에서 갱신되는 지표를 사용하면 Context가 가리키는 기준 출처와 적용 시점을 확인하고 기억에 의존한 지표 구성이나 임계값을 강제하지 않습니다.

`SQ-2`에서는 framework가 기본 escaping을 제공한다는 사실이나 보안 도구가 구성됐다는 사실만으로 XSS 방어를 확정하지 않습니다. 사용자 입력, API 응답, URL·storage 값, 외부 HTML·Markdown과 같은 신뢰하지 않는 출처에서 text, HTML, DOM, URL, script 관련 출력 위치까지의 실제 흐름을 조사합니다. Raw HTML·DOM API, HTML·Markdown renderer, sanitization 구성, 우회 지점과 적용되는 테스트를 함께 확인하며 입력 검증(`TB-2`)과 출력 보호(`SQ-2`)를 독립적으로 대조합니다. 조사 범위와 근거가 부족하면 XSS가 없다고 결론 내리지 않고 `미확인`, `대조 불가` 또는 `미실행`을 유지합니다.

## 6. 근거가 있을 때만 구현 대조하기

다음 차원을 분리합니다.

- 스택 준수: `기본 일치`, `허용된 선택`, `불일치`, `기준 미결정`, `미확인`, `해당 없음`, `범위 밖`
- 현재 상태: `구현됨`, `부분 구현`, `미구현`, `계획`, `범위 밖`, `폐기·대체됨`, `미확인`, `해당 없음`
- 대조: `일치`, `문서-코드 불일치`, `대조 불가`, `미대조`, `계획이라 대조하지 않음`
- 검증: `통과 증거`, `실패 증거`, `부분 증거`, `미실행`, `실행 차단`, `해당 없음`

코드, CI 또는 runtime을 이용할 수 없다면 구현 상태를 추론하지 않습니다. 상황에 맞게 `미확인`과 `대조 불가` 또는 `미실행`을 사용합니다. Context가 요구하는 실제 명령어, 결과 및 환경 근거 없이 작업이 완료됐다고 하지 않습니다.

## 7. 주제와 규칙별로 발견 사항 보고하기

[_comparison-statuses.md](_comparison-statuses.md)의 쉬운 보고 라벨을 사용해 결론부터 이해할 수 있는 간결한 보고서를 만듭니다. 쉬운 라벨은 정확한 세부 상태를 숨기거나 합치기 위한 것이 아니라 사용자용 요약 계층입니다.

보고서 첫 부분에 우선순위가 높은 발견 사항을 다음 형식으로 둡니다.

```text
쉬운 결과 | 대상 | 쉬운 설명 | 근거 | 영향 | 다음 행동
```

설명은 상태 이름을 되풀이하지 말고, 무엇이 없거나 낡았거나 구현되지 않았는지를 프로젝트 용어로 씁니다. 예를 들어 `Context 부족 — 답변 상태: 미답` 대신 `Context 부족 — 로그인 실패 시 사용자에게 보여줄 메시지와 재시도 규칙이 문서에 없습니다`처럼 씁니다. 파일 경로, 코드 위치 또는 실행 결과를 근거로 붙이고 가장 작은 다음 행동을 제시합니다.

그다음 다음 내용을 담습니다.

1. 감사 범위와 목록 작성 방법
2. 대상 에이전트 및 작업 범위의 유효한 Context 라우팅 지도
3. 8개 주제의 질문-경로 범위 표
4. 전체 감사에서는 모든 Baseline FTS 항목을, 작업 범위 감사에서는 연결된 모든 항목을 다루는 FTS 기술 스택 표
5. runtime 12개, 코드 설계·성능·보안 5개, 근거 4개로 구분한 21개 최소 규칙·거버넌스 경로 표
6. 쉬운 결과 라벨, 소스 위치와 영향을 받는 주장을 포함한 우선순위 높은 발견 사항
7. 문서 충돌, 소유권 공백, 깨진 라우팅, 링크 전용 target 및 누락된 근거
8. 코드·runtime 제한과 `미확인`, `대조 불가`, `미실행`으로 표시된 항목
9. 가장 작은 다음 검증 또는 문서화 행동

다음과 같은 행 형식을 사용합니다.

```text
주제/ID | 쉬운 결과 | 적용 상태 | 질문·규칙 | 경로 선언 | 대상 | 에이전트/범위 | 로드 방식 | 실제 읽음 | 경로 상태 | 결함 원인 | 답변 상태 | 정본/근거 | 현재 상태 | 대조 상태 | 검증 상태 | 발견 사항
```

조직 준수 여부를 Context-코드 일관성과 혼동하지 않도록 별도의 FTS 행 형식을 사용합니다.

```text
FTS ID | 쉬운 결과 | 결정 항목 | Baseline 상태·기준 | Context 경로·선택 | 실제 선택·근거 | Context 적합성 | 구현 적합성 | 경로·답변 상태 | Context-코드 대조 | 검증 | 발견 사항
```

상태는 점수가 아닙니다. 알 수 없음, 확인 불가, 차단 및 미조사 상태를 통과·실패 숫자로 바꾸지 말고 그대로 유지합니다. 쉬운 결과만으로 세부 표를 대체하지 않으며, `Context 부족`, `Context 부패`, `미구현`의 판정 근거가 되는 경로·답변·현재·대조·검증 상태를 함께 남깁니다.

## 올바른 감사의 품질 기준
