# 프로젝트 Context 스캐폴드

Baseline 프로젝트 셋업의 셋업 여부 gate를 통과한 초기화되지 않은 대상에 프로젝트 Context와 에이전트 진입점을 생성하거나 통합할 때 이 문서를 읽습니다. `이미 셋업됨` 또는 `판정 보류` 대상에는 이 문서의 생성 절차를 실행하지 않습니다.

## 필수 결과

구성된 모든 프로젝트에는 다음이 있어야 합니다.

1. 작업을 적용되는 프로젝트 소유 사실과 규칙으로 직접 연결하는 `AGENTS.md`의 `Context 인덱스`와 이를 불러오는 `CLAUDE.md`의 `@AGENTS.md` import
2. Baseline의 8개 Context 주제와 공통 코드 설계·성능·보안 기준을 빠짐없이 다루되, 프로젝트 산출물별로 사실의 정본 소유권을 나눈 8개 문서
3. 에이전트에게 기본 `software.md`와 적용되는 모든 추가 문서를 읽도록 명시적으로 지시하는 대상 프로젝트 활성 지침 루트의 `AGENTS.md`와, 그 정본으로 라우팅하는 `CLAUDE.md` 진입점
4. 조직 Baseline을 프로젝트 근거로 복사하지 않고 작성한 프로젝트별 현재 상태, 규칙, 결정, 계획, 소유자 및 근거

진입점은 탐색 및 작업 지침이지 중복 Context 저장소가 아닙니다. 정본 명령어, 스택 선택, 아키텍처 사실 및 결정 이력은 사용자가 선택한 Context 보관 폴더 또는 프로젝트에 확립된 동등한 위치에 둡니다.

## Context 보관 폴더 선택

새 Context 소유 위치가 필요할 때 사용자가 요청에서 이미 경로를 지정했다면 그 값을 사용합니다. 그렇지 않으면 다음 질문으로 한 가지를 반드시 선택받습니다.

```text
Context 문서를 보관할 폴더를 선택해주세요: context, docs, sot, 직접 입력
```

- `context` → 대상 프로젝트의 `context/`
- `docs` → 대상 프로젝트의 `docs/`
- `sot` → 대상 프로젝트의 `sot/`
- `직접 입력` → 사용자가 이어서 입력한 대상 프로젝트 상대 경로

기본 선택을 두지 않으며 사용자 대신 추론하지 않습니다. 직접 입력값은 비어 있지 않은 정규화된 상대 경로여야 합니다. 절대 경로, `..`로 대상 프로젝트를 벗어나는 경로, 대상 루트 자체를 뜻하는 `.`은 거부하고 다시 입력받습니다. 선택 경로가 이미 존재하면 내용을 조사하고 충돌 여부를 확인한 뒤 씁니다. 폴더 선택은 기존 파일 덮어쓰기를 허가하지 않습니다.

Gate를 통과한 대상 또는 허용된 상위 지침 범위에 유효한 Context 소유 문서가 이미 있으면 그 위치를 보존하고 다시 묻지 않습니다. 새 위치를 만들어 기존 정본과 경쟁시키지 않습니다. 기존 경로를 옮기라는 별도 요청이 있을 때만 이동 범위와 참조 갱신을 확정합니다.

## 새 프로젝트 기본 구성

동등한 Context 경로가 없으면 [assets/project-context](../assets/project-context)의 에이전트 템플릿과 `context-files/` 문서 템플릿을 사용자가 선택한 `{{CONTEXT_폴더}}`에 다음 구조로 렌더링합니다.

```text
AGENTS.md
CLAUDE.md
{{CONTEXT_폴더}}/
|-- prd.md
|-- domain.md
|-- data-model.md
|-- ui-ux.md
|-- software.md
|-- system.md
|-- security.md
`-- decision.md
```

8개 문서는 Baseline 질문과 일대일로 대응하지 않습니다. 프로젝트 산출물별 소유권을 가지며, 고정된 Baseline 8개 주제를 다음과 같이 누적해서 다룹니다.

| Baseline 주제 | 기본 Context 소유 문서 |
| --- | --- |
| Product & Domain (제품·도메인) | `prd.md`, `domain.md` |
| Stack & Commands (기술 스택·명령어) | `software.md`, `system.md`, `security.md` |
| Structure & Routing (구조·라우팅) | `software.md` |
| State Ownership (상태 소유권) | `software.md`, `data-model.md` |
| UI & Styling (UI·스타일링) | `ui-ux.md`, `software.md` |
| Data Access (데이터 접근) | `system.md`, `data-model.md`, `software.md`, `security.md` |
| Verification (검증) | `software.md`, `system.md`, `ui-ux.md`, `security.md` |
| Decisions (의사결정) | `decision.md` |

하나의 Baseline 주제가 여러 문서에 걸칠 수 있지만 같은 사실을 복제하지 않습니다. 예를 들어 UI 기대값은 `ui-ux.md`, 이를 실행하는 테스트 명령어와 gate는 `software.md`가 소유합니다. 이미 소유자가 확립된 저장소에는 경쟁 문서를 만들지 않습니다.

공통 코드 품질·설계 기준의 정본은 `software.md`가 소유하고, gate의 통과 조건·적용 범위·예외와 컴포넌트·모듈 책임, 비즈니스 규칙 최종 구현 소유자, 공개 surface·계약과 의존성 방향을 기록합니다. 사용자 체감 성능 목표는 `ui-ux.md`, lab·field budget과 검증 gate는 `software.md`, 운영 field 수집·경보는 `system.md`가 소유합니다. 공통 보안 기준은 `security.md`가 소유하며 보안 통제·취약점 처리와 XSS 방어를 기록합니다. 실제 구현·구성·CI·테스트·runtime 결과는 이 문서들의 주장을 뒷받침하는 근거이며 Context 소유자를 대신하지 않습니다.

## 그대로 복사하지 말고 렌더링하기

- 모든 `{{...}}` 표시를 프로젝트별 값으로 교체합니다. 적용되지 않는 예시 행이나 섹션은 제거합니다.
- `{{CONTEXT_폴더}}`는 선택된 대상 프로젝트 상대 경로로 교체합니다. 이 표시는 `AGENTS.md`의 Context 인덱스와 Context 문서 템플릿에서 모두 같은 경로를 사용해야 합니다. `CLAUDE.md`에는 복제하지 않습니다.
- 지정된 Baseline에서 확정 FTS 표를 동적으로 채웁니다. 템플릿의 예시 표기를 남기거나 알려진 FTS 개수를 하드코딩하지 않습니다.
- 사실을 `현재 상태`, `규칙`, `결정`, `계획`으로 기록합니다. 연기된 통합을 설치 또는 구성된 것으로 표현하지 않습니다.
- 셋업 중 정말로 확정할 수 없는 사실은 `미확인` 또는 `미결정`으로 작성하고, 결정 소유자와 다음 행동을 명시합니다. 추측하지 않으며, 빈 제목을 답변 범위가 있는 것처럼 남기지 않습니다.
- 저장소 상대 경로와 정확히 실행 가능한 명령어를 사용합니다. 실제로 존재하는 manifest, lockfile, 구성, 소스, CI 및 배포 소유자를 가리킵니다.
- 셋업 중 이루어진 선택으로 정당화되는 결정 기록만 추가합니다. 템플릿 예시는 프로젝트 결정이 아닙니다.
- Context에 비밀값과 자격 증명 값을 넣지 않습니다. 변수 이름, 주입 경계 및 소유자만 문서화합니다.

## 라우팅 규칙

`AGENTS.md`의 Context 인덱스는 작업 조건을 적용되는 모든 소유 문서에 직접 연결해야 합니다. 경로는 누적됩니다. 데이터 기반 UI를 변경하는 작업은 처음 일치하는 행만이 아니라 `prd.md`, `domain.md`, `data-model.md`, `ui-ux.md`, `software.md`, `system.md`, `security.md` 중 영향을 받는 문서를 모두 따릅니다. `CLAUDE.md`는 `@AGENTS.md`로 이 정본을 불러옵니다.

`AGENTS.md`에는 다음 정보가 표시되어야 합니다.

- Context 문서가 위치한 `{{CONTEXT_폴더}}/`
- 항상 먼저 읽는 `{{CONTEXT_폴더}}/software.md`
- 8개 문서 각각의 실제 경로, 정본 소유 내용 및 읽기 조건
- 일치하는 읽기 조건은 누적되고 영향을 받는 consumer와 의존성도 따라간다는 규칙

일반 Markdown 링크를 별도 인덱스 대신 사용하지 않습니다. 경로와 조건은 `AGENTS.md` 본문에 직접 표시하고, Claude Code의 지원되는 import 문법인 `@AGENTS.md`만 `CLAUDE.md` 라우팅에 사용합니다. 인덱스를 변경할 때 `CLAUDE.md`에 내용을 복제하지 않습니다.

기본 인덱스는 최소한 다음과 같이 연결해야 합니다.

- 모든 작업 → `software.md`
- 제품 목적, 사용자, 요구사항, 핵심 흐름 및 지도 필요 여부 변경 → `prd.md`
- 도메인 용어, 비즈니스 규칙 및 불변 조건 변경 → `domain.md`
- entity, schema, 관계, 영속성 및 migration 변경 → `data-model.md`
- 화면 구조, 상호작용 상태, 지도 UI, 반응형, 접근성 및 사용자 체감 성능 목표 변경 → `ui-ux.md`
- rendering, application 기반, 지도 engine·client boundary, 모듈·컴포넌트 책임, 비즈니스 규칙 구현 소유자, 공개 surface·의존성, route, 상태·cache 소유권, 생성 코드, 개발 명령어, 코드 품질 기준·gate·예외, lab·field 성능 budget·검증 변경 → `software.md`
- rendering·hosting 호환성, 지도 provider·공간 데이터, API, 외부 입력, 인증, 권한, 환경, cache·revalidation, 운영 성능 수집·경보, 런타임 및 배포 변경 → `system.md`
- 보호 자산, 위협·오용, 지도 credential·외부 입력, 신뢰 경계, 신뢰하지 않는 콘텐츠 출력·raw HTML·DOM·XSS 방어, 비밀값, 의존성 공급망, 보안 통제·취약점·예외 및 보안 검증 변경 → `security.md`
- 지속되거나 기존 결정을 대체하는 선택 → `decision.md`
- 각 작업 → consumer 또는 의존성을 통해 영향을 받는 추가 주제

## 기존 저장소의 초기화되지 않은 대상에 통합하기

이 섹션은 `frontend-project-setup.md`의 셋업 여부 gate를 통과한 대상에만 적용합니다. 이미 프로젝트가 셋업된 대상의 Context나 에이전트 지침을 보완하는 데 사용하지 않습니다.

쓰기 전에 기존 지침과 Context 파일의 목록을 만듭니다. 그다음 다음을 수행합니다.

1. 각 주제의 현재 정본 소유자를 식별하고 사용할 수 있으면 유지합니다.
2. 누락된 질문과 사실의 소유권을 기존 Context 문서에 추가합니다.
3. 관련 없는 지침을 삭제하지 않고 `Context 인덱스`를 기존 `AGENTS.md`에 병합하며, `CLAUDE.md`에는 `@AGENTS.md` import를 추가합니다. 기존 Claude 전용 지침은 보존하되 Context 인덱스는 복제하지 않습니다.
4. 루트와 중첩 지침의 범위 및 저장소 우선순위를 보존합니다.
5. 중복되거나 모순되는 소유자 중 하나를 조용히 선택하지 말고 명시적으로 해결합니다.
6. 소유자가 정말로 누락된 사실에만 기본 소유 문서를 만듭니다.

허용된 대상이 모노레포 안에 중첩되어 있다면 추가 권한 없이 대상 밖의 상위 지침 파일을 변경하지 않습니다. 대상 내부의 유효한 경로 범위 진입점을 우선합니다. 기존 파일명이 다르면 활성 `AGENTS.md` 인덱스가 실제 경로를 가리키고 `CLAUDE.md` import가 해당 파일을 올바르게 해석하는지 확인합니다. 내용이 달라질 수 있는 별칭을 만들지 않습니다.

## 완료 검사

이름만 확인하지 말고 렌더링된 파일을 조사합니다.

- `AGENTS.md`에 `Context 인덱스`가 직접 표시되고 `CLAUDE.md`가 `@AGENTS.md`로 라우팅됩니다.
- 인덱스가 일치하는 경로는 누적된다고 설명하며, 8개 대상 경로가 모두 해석됩니다.
- 선택한 Context 보관 폴더에 별도의 `README.md`를 생성하지 않았습니다.
- Baseline의 8개 주제와 공통 코드 설계·성능·보안 기준이 8개 소유권 문서에 빠짐없이 연결되고, 중요한 각 사실에는 발견 가능한 정본 소유자가 하나씩 있습니다.
- 선택된 FTS 행, 명령어 및 근거가 생성된 구성과 일치합니다.
- `{{...}}` 표시, 예시 기록, 만들어낸 주장 또는 실제 자격 증명이 남아 있지 않습니다.
- 편차와 미확정 항목에 소유자 및 다음 행동이 있습니다.
- 셋업 검증 결과는 실제로 실행한 명령어만 기록합니다.
